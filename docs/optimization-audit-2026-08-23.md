## 完成情况

### 1. M2 与 M1–M6 同级

M2 的正式实现已迁移到 `hypoforge/modules/m2_literature/`。旧的
`hypoforge/literature` 只保留兼容入口，生产代码全部引用新位置；兼容测试证明
旧、新导入得到同一组类对象，避免迁移后出现双注册或类型不一致。

### 2. M4 → M2 证据缺口回访

M2 现在同时接收 M4 的 `EvidenceGapRequest` 和 M6 的 `EvidenceGap`，按问题去重，
但分别保存来源 ID。只有实际取得检索结果的缺口才会被推进状态；某个缺口失败时，
不会误把其他未检索缺口标成已处理。

离线集成测试验证的真实调度顺序为：

`M1 → M2 → M3 → M4 → M2 → M3 → M4 → M5 → M6`

### 3. 用途感知上下文管理

M4、M5、M6 不再统一读取整份图谱文本，而是根据用途构建独立上下文包：

- M4：生成、批判、排序；
- M5：按假设聚焦研究计划；
- M6：科学逻辑、方法可行性、证据充分性。

每个上下文包都包含预算、估算 token、纳入/裁剪条目 ID、裁剪原因和渲染哈希。
原始提示词不写入事件日志，但完整来源 ID 可审计。

大型图谱边界修复后，裁剪 ID 不再反向挤占 LLM 提示词预算；最终裁剪优先保留
focus 证据。基准数据：

- 旧上下文估算：60,080 token；
- 新上下文估算：28,403 token；
- 估算降幅：52.72%；
- 丢失 focus ID：0。

### 4. 网页界面

- 首页凭证默认收起，减少首屏空白；
- 新增独立视觉样式层，并通过白名单静态资源路由加载；
- 保留原有 M1–M6 详情抽屉、M3 图谱、迭代和回跳时间线；
- 新增“上下文预算”面板，实时显示上下文包、估算输入 token、纳入证据和裁剪记录；
- 420 px 窄屏无横向溢出，上下文指标自动变为两列；
- 静态资源路径遍历测试通过。

### 5. 真实运行追加修复

第一次真实快速运行发现：模型把全部实体标成 `method/outcome` 时，M1 的快速路径
没有必需 `primary_object`，最终硬校验直接终止。现已在不新增实体的前提下，从
已通过原问题来源检查的实体中提升一个主对象，并生成 `m1_contract_repaired`
审计事件。

第二个问题是快速模式把全文目标设为 0，但旧表达式使用
`configured_target or final_k`，导致 0 被错误替换为 2，继续执行预印本补搜。
现已保留显式 0，并在快速预设中关闭预印本补搜。

### 6. 真实 Token 归因与快速模式 M2 精简

供应商返回的 usage 现在由每次 Pipeline 独立的 `contextvars` 计数器记录，避免
并发网页运行互相串账。M1–M6 重复回访会累计到稳定的模块名；Pipeline 后的独立
评分单独计数，不再伪装成 M6 成本。M2 并发 Tool 另有子作用域，所以 Query
Planner、Scout 和 Paper Reader 的用量不会互相重复统计。网页新增真实 Token
分布条形图；旧历史记录没有模块明细时明确提示，而不是把各模块错误显示为 0。

同一真实问题的快速模式前后对照如下。三轮均从 M1 跑到 M6、生成假设与方案，
状态错误数均为 0；由于模型采样，子问题数和 M5 是否触发结构化重试会波动，耗时
不能只由 Token 单变量解释。

| 版本 | 子问题 | 论文 | 知识条目 | M2 调用 | M2 Token | 全链路 Token | 耗时 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 原快速逻辑 | 3 | 5 | 11 | 26 | 59,885 | 76,083 | 92.8s |
| 精简辅助判定 | 2 | 4 | 10 | 8 | 30,306 | 43,330 | 65.6s |
| Scout 输入压缩 | 2 | 4 | 7 | 8 | 25,820 | 45,268 | 97.1s |
| M5 单次生成 | 3 | 6 | 11 | 12 | 41,114 | 56,440 | 75.5s |

“精简辅助判定”只作用于快速模式：保留语义 Scout 和 Paper Reader，把补充实体、
must/unmust 分类与分组、边界保留复审、实体同一性复审切换到代码中原有的确定性
回退。标准模式的 LLM 审核完全不变。Scout 仍审阅最多 8 篇候选，但快速模式将
每篇筛选文本从最多 6,000 字符缩至 1,800 字符；该轮 Scout Token 从 16,964
降至 13,908（约 18%）。第三轮总耗时上升是 M5 首次结构化输出未通过校验并自动
重试一次，M5 从 1 次调用变成 2 次，并非 M2 变慢。

快速模式的 M5 也不再因为词面任务锚点缺失而重新生成整套方案：第一次输出若结构
有效，只将原始研究目标确定性写回 `study_subjects`，随后重新建立 task trace；
校准仍失败才使用原有兜底方案。第四轮真实运行含 3 个子问题，M5 仅调用 1 次，
保留模型生成的 5 步研究流程并在 75.5 秒内完成。标准模式仍保留双轮生成与语义
对象审核。

### 7. 标准模式基线与后续优化

同一 RAG 科学问答问题的标准模式完整运行成功完成两轮证据迭代，实际路径为：

`M1 → M2 → M3 → M4 → M5 → M6 → M2 → M3 → M4 → M5 → M6`

该轮取得 10 篇论文、48 条知识条目，运行状态错误数为 0，总耗时约 28 分 22 秒。
Pipeline 内模型用量为 198,294 input + 86,667 output = 284,961 token；最终独立
评分另用 11,847 token，总计约 296,808 token。按模块累计如下：

| 模块 | 访问次数 | Input token | Output token | 调用数 | 累计耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| M1 | 1 | 7,746 | 15,201 | 11 | 269.5s |
| M2 | 2 | 74,396 | 32,067 | 39 | 404.2s |
| M3 | 2 | 11,295 | 2,324 | 6 | 51.2s |
| M4 | 2 | 50,859 | 28,559 | 10 | 633.1s |
| M5 | 2 | 11,084 | 4,727 | 4 | 89.1s |
| M6 | 2 | 42,914 | 3,789 | 8 | 78.4s |

主要瓶颈已经从笼统的“模型慢”定位到具体 Tool：第二轮 M4 的
`hypothesis_generator` 单次为 244.1 秒；M2 是最大的 Pipeline token 消耗模块；
最终评分中 `evidence_consistency` 用时 146.6 秒。后续优化必须分别处理，不能只把
全局超时继续放大。

M1 的主分解仍保留模型思考；覆盖检查、合并、补充、实体抽取与审核、需求映射、
追问路由等结构化辅助调用关闭额外 thinking。这些调用的语义步骤和结构化校验均
保留，只减少隐藏推理输出。OpenAlex 对短暂 429 增加了受阶段 deadline 约束的
重试，并用可配置的最小请求间隔降低同轮补搜的突发请求碰撞。

同一问题的标准 M1 复测从 269.5 秒降至 80.8 秒（约 -70.0%），从 22,947 token
降至 8,390 token（约 -63.4%）。主分解仍使用 61.9 秒和 3,483 output token；
其后覆盖审核、实体抽取、实体审核和需求映射分别只需 3.0、6.2、5.6、4.0 秒。
输出仍包含 2 个覆盖原问题两项目标的子问题、4 个关键实体和 2 条原子需求。

用同一份第一轮 M3 快照对 M4 做严格前后对照：Generator 继续保留 thinking，
合同审核、Critic、可证伪性检查和 Ranker 改为结构化直接回答。模块耗时从
272.8 秒降至 157.9 秒（约 -42.1%），output token 从 15,454 降至 8,719
（约 -43.6%）；仍产出 2 个通过门槛的候选和 1 个最终假设。各辅助 Tool 的耗时
变化为 Critic 87.8→9.6 秒、可证伪性 23.2→6.4 秒、Ranker 35.7→6.3 秒。
Generator 本身因模型采样从 119.6→129.1 秒，仍是后续优化的主要对象。

### 8. M6 评分职责纠正

标准实测发现，M6 内部曾调用三项“独立指标”，但 Pipeline 以 `mod(state)` 形式
调用模块，`config` 参数实际为 `None`。因此该调用没有评测模型配置，产生的是降级
0 分，却被追加到 M6 review 并参与总体分数；链路结束后又会用真实配置重新执行
同样的独立评分。

现将职责拆清：M6 只保留任务对齐、两个专家审核和三个确定性质量门槛，用于决定
是否迭代；`evidence_consistency`、`novelty`、`testability` 仅由 Pipeline 结束后的
权威独立评分计算一次。没有复用 M6 的旧结果，因为旧结果并不等价于真实评分。

### 9. `.env` 检索凭证实际传递

真实 M2 日志暴露出一个状态与执行不一致问题：Web 后端能从环境变量判断
OpenAlex/Semantic Scholar“已配置”，但只把网页请求体中显式填写的值传给本轮
M2。若服务启动后才加载外部 `.env`，部分 Tool 模块已在 import 阶段缓存了空值，
于是页面显示有 key，实际请求仍可能走匿名额度。

RunManager 现统一解析“网页输入 → YAML → 环境变量”的有效凭证，并只在内存中
交给本轮 worker；OpenAlex、Semantic Scholar、Serper、ADS、Unpaywall、Crossref
均适用。公开运行记录、manifest 和事件仍只保存布尔状态与警告，不落盘密钥。

修复后的真实快速链路中，OpenAlex 返回 18 条、arXiv 返回 6 条，没有再出现匿名
额度 429；M2 最终采纳 4 篇论文并提取 7 条知识，耗时 29.1 秒。

### 10. 快速模式 M4 长尾兜底

同一真实快速问题的第一轮验证中，Generator 与一次补生返回的 6 个候选均未通过
任务合同。旧流程仍发起第三次 `hypothesis_contract_repair`，等待 90 秒超时后才
使用确定性兜底；虽然全链路最终 0 错误完成，但总耗时达到 173.5 秒。

快速模式现在最多执行一次生成和一次补生；若仍没有合同合格候选，直接生成可供
M5 使用的确定性兜底假设，不再发起第三次 LLM 修复。标准模式仍保留合同修复。
重启后同题真实链路在首轮即取得 1 个合同合格候选，M4 用时 13.1 秒，全链路
63.9 秒完成、0 个状态错误；独立的回归测试覆盖“首轮和补生均为空”分支，并验证
合同修复调用次数为 0。

### 11. 独立证据一致性批量评分

旧 `evidence_consistency` 先把最终假设拆成原子主张，再为每一条带威胁上下文的
主张串行调用一次模型；标准基线的 4 条主张因此产生 5 次调用（1 次拆分 + 4 次
冲突判定）。现保留逐主张的 embedding/关键词召回与完整 trace，但把所有冲突判定
合并成一个带稳定 `claim_index` 的结构化批次；缺失 verdict 不再被误当作“一致”。

同一份最终状态的真实重放结果：整套独立评分从约 176 秒、7 次调用、11,847
token，降至 57.7 秒、4 次调用、7,261 token。输出仍包含 4 条原子主张各自的
命中节点、威胁节点、冲突布尔值与理由。由于 LLM judge 会重采样，证据一致性从旧
报告的 0.50 变为本轮 0.75；创新性 0.70、可测性 1.00 不变。验收以逐项 trace
完整和结构化覆盖为准，不要求随机评测的浮点结果逐次完全相同。

### 12. 标准模式 M4 超时恢复与反馈重生限时

新标准链路完整走过第一轮 `M1→M6`，并由 M6 提出 2 个证据缺口，随后真实执行
`M2→M3→M4`。第二轮 M4 主 Generator 在模块配置的 360 秒单次上限处触发
`TimeoutError`；旧逻辑在标准模式直接向外抛出，导致已经运行 27 分 16 秒的整条
链路丢失继续执行机会。这里确认是明确的单次调用超时，不是网页假死或后端死锁。

现在首轮 Generator 仍保留 thinking；仅当单次生成真的超时且模块共享总预算仍有
余额时，自动用同一份图谱上下文执行一次 `hypothesis_generator_timeout_recovery`，
并关闭扩展 thinking。共享总预算已经耗尽时仍维持原有超时语义，不会越过 Pipeline
设定的硬边界。Critic/可证伪性把全部候选判退后的反馈重生也关闭扩展 thinking：
此时已有明确审核意见，不需要再次进行数分钟开放式推理。

真实恢复验证复用了失败前保存的第二轮 M3 快照，并把首轮窗口临时压到 60 秒以
稳定触发恢复分支。结果在 214.3 秒内完成严格 M4：首轮超时后恢复生成 3 个候选，
Critic 全退后又按批评意见重生；任务合同剔除 1 个缺少 `hallucinations` 核心实体的
候选，最终 1 个候选通过复审和排序，未把超时抛给流水线。该验证同时覆盖了两条
新的真实模型恢复路径，而不只是模拟单元测试。

随后又通过网页 `resume_of` 从原失败运行的第二轮 M3 快照续跑，使用正式 360 秒
单次上限：主 Generator 再次稳定触发超时，事件流自动切换到 timeout recovery，
恢复生成仅用 45.8 秒；之后 M4 审核排序、M5、M6 和三项独立评分全部完成。续跑
总耗时 9 分 44 秒、流程错误 0，证明恢复逻辑在真实 Web worker 中同样生效，而非
只在直接调用模块时成立。

### 13. 标准模式 M2 Scout 成本上界

标准链路两次 M2 的 Tool 归因显示，Scout 共 16 次模型调用、100,682 token，明显
高于 Query Planner 和 Paper Reader，是 M2 最大的单项成本。网页标准配置原先允许
每轮最多 24 篇候选进入语义 Scout，即最多三个 8 篇批次。现将上限保守收紧到
16 篇；更低排名的论文不会被删除，而是继续使用代码中已有的保守词法 note 参与
后续筛选，因此这是 LLM 成本上界，不是硬截断论文池。

使用同一份 M1 快照真实重放 M2：历史 24 篇配置取得 12 篇记录、46 条知识、
94,473 token；16 篇配置取得 13 篇记录（8 篇唯一论文）、57 条知识、93,480
token，三个子问题均为 0 个错误。净 token 仅下降约 1.1%，因为本轮最终多读了
1 篇论文，Paper Reader 的新增成本抵消了部分 Scout 节省；外部 Crossref 限流也
使墙钟耗时不可直接比较。该调整仅作为保守的极端成本边界，不继续压缩到 8 篇，
以免对跨领域问题的语义召回造成不可控损失。

### 14. M6 最终任务对齐与独立评分一致

标准续跑成功后发现同一结果存在互相矛盾的判定：M6 运行中把任务对齐评为满分并
给出总体 4.2/5，但 Pipeline 末尾独立质量门槛判定失败。根因是 M4 允许候选只声明
自己覆盖的原子需求子集；M5 与旧 M6 都沿用该子集，而末尾评分按 M1 的完整任务
契约检查。该轮最终假设和方案只记录了 R1、R2，遗漏“同时平衡幻觉降低与答案
相关性”的 R3，因此被旧 M6 隐藏、被末尾评分发现。

M4 仍可生成针对局部子问题的候选，但 M6 审批最终假设—方案对时，现统一按完整
M1 契约检查全部 required requirement，不再相信候选自行缩小的 trace 范围。使用
同一真实最终状态重放新版 M6：明确报告假设与方案均缺少 R3，任务对齐降为 1.0，
总体分从 4.2 封顶到 1.9，hard gate 为 false；其他专家审核调用保持不变。这样
缺项会成为迭代反馈，运行期审核与末尾独立评分不再互相矛盾。

### 15. 快速模式唯一方案覆盖完整问题

M6 改为检查完整任务契约后，同题快速全链路仍在 63.15 秒、0 错误下返回假设和
方案，但首次如实暴露出 M4 只声明 R1、遗漏 R2，任务对齐与总体分分别被封顶为
1.0 和 1.9。标准模式可以用评审迭代补齐，快速模式没有后续回路，因此仅在快速
M4 的任务契约提示中增加一条硬约束：每个一遍式最终候选必须真正覆盖所有 required
requirement，并为每个 ID 提供字面可审计 trace。标准模式仍允许候选分别探索局部
子问题，由 M6 在最终审批时检查组合结果。

复用该轮 M3 快照真实重放快速 M4–M6：34.38 秒完成、2 次模型调用；最终假设和
研究方案的 requirement trace 均为 `[R1, R2]`，M6 任务对齐恢复为 5.0，总体
4.8。第一批中两个漏必需实体的候选仍被原有契约门槛剔除，说明新提示没有削弱
现有硬校验。

### 16. 标准模式迭代轮 M4 关闭重复长思考

标准模式第一轮 M4 继续保留扩展 thinking，以保证开放式假设探索；但第二轮及
后续迭代已经拥有上一轮假设、审核反馈和更新后的证据图谱，不再重复进行开放式
长思考。真实日志中第二轮 Generator 曾连续在 360 秒单次上限处超时，而同一上下文
关闭 thinking 后能在约 46 秒生成可通过严格门控的候选。因此现在仅当
`iteration_count > 0` 时，主 Generator 直接使用结构化非 thinking 调用；首轮标准

## 尚存风险（不阻塞当前版本）

1. arXiv 出现过瞬时网络超时。流程能用 OpenAlex 结果继续完成，但快速模式的
   总耗时仍可能被来源级超时拉长。
2. “上下文预算”仍是本地确定性估算；新增“真实 Token 归因”来自供应商响应的
   usage。若某个兼容模型不返回 usage，该次调用只能计时、无法得到权威 Token。
3. 快速模式的实体角色提升保证流程连续，且有审计事件；它不等价于标准模式的
   独立实体复核，因此角色语义可能较粗。
4. M4 → M2 回访已通过确定性端到端调度测试；真实外网运行只有在 M4 实际提出
   证据缺口时才会自然触发，不能靠普通问题强制复现。
5. 标准模式 M4 仍是最大耗时模块；在降低其 thinking 或进一步压缩上下文前，需要
   用同一份 M3 状态做前后质量对照，不能只以速度决定默认策略。
