# 检索契约与综合契约分离设计

## 目标

M1 生成的子问题仅用于帮助 M2 完整检索文献，并由 M3 保留证据来源。
M4、M5、M6 不再读取或按这些子问题生成、设计、评分，而是始终围绕用户的
原始问题工作。每个 M4 候选都必须独立回答原问题，而不是候选组合各回答一个
子问题。

## 已确认根因

`ProblemCard.task_contract.requirements` 当前把每个 M1 子问题保存为 R1…Rn。
`build_graph_context()` 又把完整 `TaskContract` 序列化进 M4–M6 上下文，因此 M4
能看到全部子问题。M4 提示词允许候选组合拆分这些 requirement，排序却只保留
`top_k=1`；M5 只为该候选生成一个方案，而 M6 又要求这一对输出覆盖全部 R ID。
这使宽泛问题很容易被任务对齐硬门槛封顶。

## 数据边界

### 检索契约（保持现状）

- 权威数据仍为 `ProblemCard.sub_questions` 与
  `ProblemCard.task_contract.requirements`。
- M2 使用子问题和实体组合检索。
- M3 可以保留论文、知识和检索子问题之间的来源关系。
- 不改变历史快照格式，不迁移 M1/M2 已有数据。

### 综合契约（新增只读视图）

从同一 `ProblemCard` 确定性派生，不额外调用模型，也不重复持久化：

- 原问题：`ProblemCard.original_question`；
- 实体：沿用原问题提取出的 `TaskEntity`；
- 唯一综合需求：`Q0 = answer the original question as a whole`，其问题正文就是
  原问题；
- 不包含 R1…Rn、子问题文本或由子问题生成的 relation。

综合契约由一个纯函数生成，并作为显式参数交给对齐器，避免临时修改
`PipelineState`。

## 模块数据流

1. M1 继续输出原问题、实体、子问题和 R1…Rn。
2. M2/M3 继续使用检索契约，不改变搜索与图谱构建。
3. `build_graph_context()` 为 M4–M6 暴露综合契约；证据事实、冲突、知识缺口、
   引文和图关系照常保留。
4. M4 提示词仅包含原问题、原问题实体、Q0 和 M3 图谱。每个候选必须独立回答
   原问题，并为 Q0 生成可审计的字面 trace。
5. M4 的确定性合同校验与语义审核均使用综合契约。审核只比较原问题与候选，
   不读取子问题。
6. M5 继承候选的 Q0，按原问题生成和校验研究方案。
7. M6 及 Pipeline 末尾独立任务对齐统一使用综合契约，不再用检索子问题作为
   最终答案覆盖率门槛。

## 上下文隔离

当前真实运行中，三个子问题只在 GraphContext 的完整 TaskContract JSON 中出现，
证据正文没有重复它们。因此以综合契约替换该序列化字段即可切断已知泄漏。
增加回归测试，对完整 M4 Generator prompt 逐条断言：包含原问题，不包含任何
M1 子问题原文或 R1…Rn relation。

M3 基于子问题检索得到的科学事实仍会进入 M4；这是需要的知识，而不是检索控制
文本。不得因为来源是某个子问题而删除证据。

## 兼容性与失败语义

- 历史 `ProblemCard` 无需迁移，综合契约在读取时生成。
- 新生成的 M4/M5 输出使用 Q0 trace。
- 从 M3 或更早快照续跑会自然生成新 trace。
- 若直接从旧 M5 快照进入 M6，M6 在评分前根据输出中的原问题实体重新规范化
  Q0 trace；无法形成真实字面证据时仍判定不对齐，不伪造通过。
- M4 候选若只给出局部机制但没有回答原问题，综合语义审核应拒绝或触发一次
  现有的有界重生；不会自动把 R1…Rn 全部标记为已覆盖。

## 测试与验收

1. 单元测试先失败，证明旧 M4 prompt 会泄漏子问题且允许局部 requirement。
2. 验证综合契约只含 Q0、原问题和原始实体。
3. 验证 M4 Generator、合同修复、迭代提醒均不包含子问题。
4. 验证 M5/M6 和 posthoc scorer 都按 Q0 判断，结果一致。
5. 运行完整自动测试与 Python 编译检查。
6. 使用“肠道微生物组如何影响人体免疫系统？”真实重跑 M1–M6，检查：
   M4 请求无子问题；最终假设和方案为 Q0；M6 不再报告缺少 R1/R2/R3。

所有改动只保存在本地分支，未经用户再次明确授权不得推送。
